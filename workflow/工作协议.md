# 产品项目工作协议

## 项目与接续入口

- 每次接续先读项目根目录的 AGENTS.md、PROJECT.md、PROJECT_STATUS.md 和 BACKLOG.md，核对实际资料。已有 Git 仓库时检查分支、提交和未提交改动。
- 按当前任务读取相关需求、业务规则、原型、实现与验收证据。项目概况记录目标用户、业务目标、交付类型、资料入口和专属约束。
- 用户当次要求决定任务范围，纠正后同步目标和完成标准。已明确授权的工作持续执行至完成。
- 状态摘要用于定位工作。具体结论结合最新用户决定、正式资料、实际实现和验证记录核对，有冲突时先查明来源与适用版本。

## 需求与自主执行

将用户需求整理为目标、使用场景、交付物、约束和可观察的完成标准。保留用户指定的数字、对象、范围与限制。建议、已确认规则和实际实现分别登记。

| 类型 | 适用范围 | 执行方式 |
| --- | --- | --- |
| L1 执行与修复 | 已确认方案的整理或实现、有复现证据的缺陷、完成任务必要的局部维护 | 直接完成、验证并记录 |
| L2 局部设计 | 当前授权目标内的交互细节、信息展示、文档组织、可回退的实现选择 | 自主选择，交付时说明影响结果的假设与取舍 |
| L3 产品决定 | 尚未授权的核心业务规则、功能范围变化、重大技术路线及正式数据处置 | 先完成可独立开展的调查，提出具体选择，相关实施等待决定 |

- 用户已指定方案、授权试验或给予参数范围时，按既有授权执行。需要产品决定的范围以真实缺口为准。
- 按当前需求开展必要调研，结合项目资料、已有工具和可核验来源形成结果，保留依据与适用范围。
- 待办优先级决定处理顺序，授权和依赖决定可执行范围。用户要求按待办继续时，连续完成已授权且依赖满足的事项。
- 额外功能和范围外重构作为候选记录。使用决策卡片时，把当前可决定且互不影响的问题在一次提问中放入同一张卡片，每个问题单独一个页签（tab）。若某个答案会改变后续问题的选项或决定它是否需要提问，等答案确定后再问该后续问题。
- 用户确认后更新对应正式资料与待办，已有授权覆盖的事项直接执行。

### 提问后的工作与等待

1. 需要用户答复时，优先使用能在当前任务中接收回复的异步提问方式。发出问题后，继续处理本轮已授权且不依赖该答复的工作。
2. 没有可推进的独立工作时，保持当前任务并静默等待。以发出问题的时刻为起点，最多等 5 分钟；先做了独立工作，就只等剩余时间。使用能被新消息唤醒的等待方式。
3. 收到答复就结束等待，按答复继续。满 5 分钟仍未收到答复时，恢复输出，简要说明已有结果、待确认项及其影响。必须由用户决定的步骤保留为待决策；已有授权允许自主选择的事项可按原授权继续。

## 任务闭环与记录

1. 根据用户需求选取可独立验证的任务，在 BACKLOG.md 写明编号、来源、授权、完成标准及依赖，并标为进行中。
2. 核对交付类型和资料依据，确定本次范围、验证入口及必要协作。
3. 完成调研、需求整理、设计、制作或开发，执行自检，修复本任务涉及的实际缺陷。
4. 达到验收阶段后执行相应验证，保存版本、输入、操作或命令、结果与证据位置。
5. 更新涉及的正式资料、待办和项目状态。已有 Git 仓库时，验证后默认本地提交本任务文件。
6. 连续完成本次授权内依赖满足的工作。授权范围完成、依赖阻塞或用户要求停止时，记录准确接续点。

规则状态使用草稿、待确认、已确认。任务状态使用待执行、进行中、待验证、已完成、待决策、暂缓。验收完成后再标记已完成。

PROJECT_STATUS.md 保持简短的当前状态快照，仅保留当前基线、最近 1—2 轮关键交付、当前验证缺口和下一步；早期阶段或已被新方案覆盖的历史描述定期移入归档，避免干扰后续接续。

BACKLOG.md 保持稳定递增编号并在顶部注明最新已用编号，主体仅保留未完成项（待执行、进行中、待验证、待决策、暂缓）及最近 5—10 条已完成项，链接具体依据和结果。更早的已完成条目定期归档至独立归档文档（如 `docs/archive/`）；日常接续默认不读取归档文件，仅在明确需要追溯历史决策、旧方案或特定编号时按需查阅。需要独立留档的迭代或修复再建立工作记录，包含目标、决定、改动、验证、未完成项及提交信息。

## 三个 Agent 的职责

| 角色 | 负责事项 | 输出与修改边界 |
| --- | --- | --- |
| 主 Agent | 需求整理、任务拆分、调研、设计落稿、文档与原型制作、授权内实现、自检、修复和交付 | 统一修改正式文件、维护状态、执行提交并与用户沟通 |
| product | 业务规则、产品取舍、信息架构、交互及 UI 规范 | 返回有依据的结论、建议和验收点，由主 Agent 落稿 |
| qa | 独立检查需求覆盖、交付物、实现及运行结果 | 返回检查证据、可复现缺陷和验证缺口 |

具体调用场景见[协作场景与流程](Agent协作场景与流程.md)，角色加载见[配置与接续](Agent配置与接续.md)。

### 调度约定

- 按专业问题和独立交付物派发，说明问题、输入文件、版本、授权、完成标准和返回要求。
- 用户给出明确做法、同类页面已有范例或修改能当场验证时，主 Agent 直接完成。连续改同一流程时，逐处自检，在可独立验收的业务路径上合并检查。前端设计和自检参考[前端交互约定](前端交互约定.md)。
- 需要产品判断时先说清哪条规则会改变哪项决定。需要独立验收时交付一个可定位的版本、入口、样例和预期。首次派发和唤回已有角色采用相同判断条件，具体时机见[协作场景与流程](Agent协作场景与流程.md)。
- 复用对象和依据仍有效的结论。追加调用应有新证据、实质变更、未解决问题或具体复验需要。
- 产品结论固化为可执行规范，QA 按规范独立核对。主 Agent 处理意见、修复并跟进完成。
- 最多同时运行两个子 Agent，只有存在独立工作且能缩短完成时间时并行。模型及推理设置沿用当前环境默认值。
- 优先使用独立上下文和指定角色。工具仅支持通用子任务时，读取相应角色 TOML 的完整 developer_instructions，连同任务和入口传入。
- 子 Agent 向主 Agent 返回结果，调度由主 Agent 统一处理。共用窗口、端口、数据和输出目录的操作先协调。
- 工具不可用或派发失败时完成主 Agent 能执行的检查，记录独立验证缺口和后续入口。
- 在已有任务记录中简要登记调用目标、审核版本、结论、采纳情况及复验范围。

## 验证与交付

- 按实际交付类型与变更范围分层验证。调研检查来源与适用性，PRD 检查需求覆盖和规则一致性，正式实现检查实际业务行为。
- 原型与演示阶段的日常迭代默认保持极速轻量：局部页面、表单控件、样式、文案或单点配置修改，只执行类型检查与一次构建（复用构建产物直接更新预览，避免同一轮重复打包），**默认不启动浏览器子 Agent 逐页点测**，直接交由用户在预览中确认。仅在大改版、跨页面复杂状态流转或用户明确要求实测验收时，再按需启动浏览器验证关键路径。
- 区分日常迭代与不定期专项审查。原型或演示阶段的日常迭代不默认新增、维护单元测试，也不因历史专项审查记录而将日常检查升级为全站端到端回归。
- 用户主动发起的专项审查可按需开展深度排查、全链路复验或编写临时校验脚本；临时脚本、测试夹具与审查报告统一保存在独立临时目录（如 `.runtime/`），不写入正式代码仓库，也不设为日常迭代门槛。专项审查在待办和状态中标明范围，避免后续日常会话沿用其流程深度。
- 文档覆盖角色、前置条件、操作、反馈、业务规则、字段与状态，以及任务涉及的异常和边界。具体粒度遵循项目规范。
- 需执行浏览器验收的原型路径，通过实际入口检查本次涉及的正常、空态、错误态、反馈及已支持尺寸。演示数据和已实现业务能力分别记录。
- 涉及数据写入时按支持范围检查权限、重复操作、部分失败、重试、并发和历史数据兼容。
- 共用组件集中验证，后续检查实际接入，组件变更后复验受影响路径。批量交付逐批自检，在完整交付阶段集中验收。
- 偶发问题保留已查路径、缺失证据和下一次触发时的采集入口，结论限定于实际覆盖。
- 导出文档、图片或其他文件时检查实际文件。目标平台粘贴、导入或运行分别记录验证结果。
- 正式交付注明完成内容、查看入口、验证范围和待办，标题、正文、注释和提交说明围绕最终采用的状态撰写。

## 环境与版本管理

- Windows 命令默认使用 PowerShell 7+，版本不确定时检查 `$PSVersionTable.PSVersion`。工具路径按本机发现，项目资料使用相对路径。
- 文本按格式要求使用 UTF-8，修改已有文件时保留适用编码。优先复用项目工具和已有实现。
- Git 操作前检查仓库、分支及工作区，提交只包含本任务文件，保留其他改动。推送、发布和远端创建按用户授权执行并核实结果。
- 换电脑时核对实际分支、提交、未提交内容、远端状态、工具依赖和本机专有材料，先检查实际环境再接续。
